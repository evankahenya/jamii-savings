Dashed boxes happen without appearing as stages you wrote. Checkout SCM does show up as the first column in Stage View, labelled “Declarative: Checkout SCM”. Any failure stops the run at that point and skips every later stage.

Inside each deploy back up → deploy CAR → import APIs → import products → smoke test pass → save last-good CAR fail → roll everything back

1. You start the build

Jenkins UI · job page
  1. 1

    You click Build with Parameters and Jenkins shows a form with one field, DEPLOY_UP_TO.

    The choices dev, uat and prod come from the parameters { choice(...) } block in the Jenkinsfile, which the previous build saved into the job's settings.

    youjenkins coreJenkinsfile:14
  2. 2

    You pick how far to go (default dev) and click Build.

    you
  3. 3

    Jenkins puts the build in the queue and gives it the next number (#8, #9 …) from nextBuildNumber.

    If another build of this job is still running, the new one waits, because the Jenkinsfile sets disableConcurrentBuilds(). Jenkins has 2 executors (numExecutors: 2 in casc.yaml), so the build starts as soon as one is free.

    jenkins corecasc.yaml:3

2. Jenkins loads the job

not shown as a stage
  1. 4

    Jenkins looks up the job's settings to find out where the pipeline is.

    The pipeline steps live in the Jenkinsfile, so Jenkins first needs to know which repo, branch and file to get. The job says: this is a Pipeline, the script comes from Git at file:///repo, branch */main, file Jenkinsfile. It also holds the parameters for the form in step 1 and the (empty) list of triggers.

    Jenkins loaded the job into memory when it started, from its saved copy at /var/jenkins_home/jobs/jamii-api-deploy/config.xml, and every build uses that copy. Nothing is fetched from Git yet. The Job DSL plugin wrote that file at startup, from the jobs: block in casc.yaml.

    casc.yaml is never fetched from Git. The Dockerfile copies it from infra/jenkins/ on your disk into the image at build time, and Jenkins reads that copy only when it starts. Uncommitted edits to it take effect after a rebuild. The Jenkinsfile and ci/ scripts are the opposite: only committed code is used, fetched from Git on every build (step 5).

    jenkins corejob-dsl (at startup)configuration-as-code (at startup)

3. Jenkins fetches and reads the Jenkinsfile

console: “Obtained Jenkinsfile from git file:///repo”
  1. 5

    The Git plugin checks out the whole repo into a side folder, jamii-api-deploy@script, so Jenkins can read the pipeline file.

    It's a full checkout because the job has lightweight(false). Git reads only committed history in /repo/.git, so uncommitted edits are invisible. /repo is your project folder, mounted read-only by compose.yaml. The Dockerfile's safe.directory '*' stops Git refusing it because of the different owner.

    git fetch --tags --force -- file:///repo +refs/heads/*:refs/remotes/origin/*
git rev-parse refs/remotes/origin/main^{commit}
git checkout -f <commit>
    gitgitcompose.yamlDockerfile
  2. 6

    Jenkins parses the Jenkinsfile as a declarative pipeline.

    The Pipeline plugins (installed together as workflow-aggregator) turn the pipeline { } block into stages and steps that can pause and resume, which approval gates need.

    workflow-aggregatorJenkinsfile
  3. 7

    Jenkins applies the pipeline's options and parameters.

    • timestamps(): every log line gets a time
    • timeout(60 MINUTES): abort the whole run after an hour, including time spent waiting at an approval
    • buildDiscarder(numToKeepStr: '20'): delete builds older than the last 20
    • disableConcurrentBuilds(): one build at a time
    • parameters: saves the DEPLOY_UP_TO choice back into the job's settings
    timestamperworkflow-aggregatorjenkins coreJenkinsfile:7–17
  4. 8

    Jenkins sets MI_PROJECT=Jamii_WSO2_Project for all stages.

    Jenkinsfile:19

4. Declarative: Checkout SCM

first column in Stage View

Jenkins adds this stage itself to every declarative pipeline. It isn't written in the Jenkinsfile.

  1. 9

    The Git plugin checks out the same commit into the build workspace, /var/jenkins_home/workspace/jamii-api-deploy.

    Every later sh and mvn command runs from this folder.

    gitgit
  2. 10

    Jenkins records which commit was built, and the commits since the last build.

    This fills the build's Changes page and the “Checking out Revision …” line in the console.

    gitjenkins core

5. Validate

stage “Validate” · sh 'bash ci/scripts/validate.sh'

Static checks on the repo. Nothing is built or sent anywhere. Every problem is listed and counted, then the stage fails if there were any.

  1. 11

    Load the shared helpers: folder paths, log helpers, and set -euo pipefail so any failed command stops the script.

    ci/scripts/common.shbash
  2. 12

    Check that every MI file is well-formed XML.

    All .xml, .dbs and .xsd files under Jamii_WSO2_Project/src/main/wso2mi.

    validate.shxmllint
  3. 13

    For every API folder in apim-apis/, check that it's complete and matches MI.

    • An MI API file exists: src/main/wso2mi/artifacts/apis/<API>.xml
    • An OpenAPI file exists: resources/api-definitions/<API>.yaml
    • api.yaml, api_meta.yaml, deployment_environments.yaml and params.yaml exist
    • params.yaml has dev, uat and prod sections
    • The context (URL path) in API Manager equals the context in MI
    validate.shxmllint
  4. 14

    Check that every policy an API uses exists in apim-policies/, both the .yaml and the .j2.

    validate.sh
  5. 15

    Check rate-limiting tiers.

    Each tier file's policyName matches its file name. Each API's tier is built in (Unlimited, 10KPerMin, 20KPerMin, 50KPerMin) or has a file in apim-throttling-policies/.

    validate.sh
  6. 16

    Check the API product (JamiiProducts).

    Its files exist, it has no instance-specific apiId/policyId lines, it only uses APIs and tiers that exist, and each resource uses the same rate limit as the API behind it, so the product can't bypass a limit.

    validate.sh

6. Build MI CAR

stage “Build MI CAR”
  1. 17

    Maven builds the MI project into a Carbon Application (CAR) file, skipping tests.

    Maven reads Jamii_WSO2_Project/pom.xml. Plugins and dependencies it doesn't have yet are downloaded from the WSO2 Nexus repositories listed in the POM and cached in ~/.m2. The output is Jamii_WSO2_Project/target/Jamii_WSO2_Project_1.0.0.car.

    # Jenkinsfile:32 — dir(env.MI_PROJECT) { … }
mvn -B clean install -Dmaven.test.skip=true
    dir stepmavenpom.xmlmaven.wso2.org

7. Test

stage “Test”
  1. 18

    Maven runs the MI (Synapse) unit tests.

    The real calls against running systems happen later, in each deploy's smoke tests.

    mvn -B test
    mavenpom.xml

8. Package APIM APIs

stage “Package APIM APIs” · sh 'bash ci/scripts/package-apis.sh'

Builds every package API Manager will need. This runs offline: apictl doesn't connect to anything here.

  1. 19

    For each API (AccountBalanceAPI, CustomersAPI, LoansAPI), build an apictl project folder in dist/stage/<API>.

    • Copy api.yaml, api_meta.yaml and deployment_environments.yaml, removing Windows line endings
    • Copy the shared OpenAPI file to Definitions/swagger.yaml
    • For each policyName in api.yaml, wrap its spec as Policies/<name>_<version>.yaml and copy the .j2 template
    package-apis.shsed · awk
  2. 20

    Zip each project with apictl and put its params.yaml beside the zip.

    params.yaml holds the backend URL for each environment, so one zip can go to dev, uat and prod unchanged.

    apictl bundle -s dist/stage/LoansAPI -d dist/apis   # → LoansAPI_1.0.0.zip
# + dist/apis/LoansAPI.params.yaml
    apictl 4.7.2package-apis.sh
  3. 21

    Copy the custom rate-limiting tiers to dist/rate-limiting-policies/.

    package-apis.sh
  4. 22

    Build and zip the API product the same way, into dist/api-products/JamiiProducts_1.0.0.zip.

    apictlpackage-apis.sh
  5. 23

    Jenkins saves the CAR and the API packages with the build and fingerprints them.

    These are the files under Last Successful Artifacts on the job page. Fingerprints let Jenkins trace which build produced a given file.

    archiveArtifacts artifacts: "Jamii_WSO2_Project/target/*.car, dist/apis/**", fingerprint: true
    archiveArtifactsJenkinsfile:50

9. Deploy: dev

stage “Deploy: dev” · deployTo('dev')

The deployTo() function at the bottom of the Jenkinsfile prepares the environment, then hands over to deploy.sh. From step 31 on, any failed command triggers a full rollback.

  1. 24

    Read the environment's settings from ci/environments/dev.properties.

    ENABLED=true
APIM_URL=https://host.docker.internal:9443      MI_MGMT_URL=https://host.docker.internal:9164
GATEWAY_URL=https://host.docker.internal:8243   MI_URL=http://host.docker.internal:8290
APIM_CREDENTIALS_ID=apim-dev-admin             MI_CREDENTIALS_ID=mi-dev-admin
    pipeline-utility-steps · readPropertiesdev.properties
  2. 25

    If ENABLED isn't true, print “placeholder – nothing deployed” and end the stage as passed.

    Jenkinsfile:85
  3. 26

    Look up the two saved logins and expose them to the script as APIM_USER/APIM_PASS and MI_USER/MI_PASS.

    The credentials were created from casc.yaml at startup. Jenkins masks the values as **** if they appear in the log.

    credentials-binding · withCredentialscasc.yaml
  4. 27

    Set TARGET_ENV=dev and the four URLs as environment variables, then run bash ci/scripts/deploy.sh.

    withEnv · shdeploy.sh
  5. 28

    Pre-flight checks: all required variables are set, there's exactly one .car in target/, and every API and product zip exists.

    deploy.shcommon.sh · require_vars
  6. 29

    Wait for MI to answer, up to 20 minutes, checking every 10 seconds.

    curl -u "$MI_USER:$MI_PASS" https://host.docker.internal:9164/management/login   # → AccessToken
    common.sh · mi_logincurl · jqMI management API
  7. 30

    Wait for API Manager to answer, then register and log in to the environment with apictl.

    curl https://host.docker.internal:9443/services/Version
apictl add env dev --apim https://host.docker.internal:9443
apictl login dev -u "$APIM_USER" --password-stdin -k
    common.sh · apim_readyapictl · curlAPI Manager
  8. 31

    Turn on the safety net: from here on, any failed command calls on_error, which runs the rollback.

    trap 'on_error $LINENO' ERR
    deploy.sh
  9. 32

    Create or update the custom rate-limiting tiers in API Manager.

    Tiers must exist before the APIs that use them. This step is not rolled back.

    apictl import policy rate-limiting -f dist/rate-limiting-policies/<tier>.yaml -e dev --update -k
    apictlAPI Manager
  10. 33

    Back up what's live now, so it can be put back if something fails.

    • Export each API. If it doesn't exist yet, note it as new: apictl export api -n <API> -v 1.0.0 -e dev
    • Export the API product and save a cleaned copy without instance IDs
    • Find the last CAR that worked for dev in $JENKINS_HOME/jamii-state/dev/last-good/
    apictl · unzip · sedAPI Manager
  11. 34

    Deploy the CAR to MI: remove the old CApp, upload the new one, and wait until it's active.

    DELETE /management/applications/Jamii_WSO2_Project_1.0.0   # then poll until absent
POST   /management/applications  -F file=@Jamii_WSO2_Project_1.0.0.car
GET    /management/applications   # poll up to 180 s until active; fail if “faulty”
    common.sh · mi_deploy_carcurl · jqMI management API
  12. 35

    Check that every API is now live on MI.

    GET /management/apis   # must list AccountBalanceAPI, CustomersAPI, LoansAPI
    deploy.shMI management API
  13. 36

    Import each API into API Manager with dev's backend URLs, as a new revision. Each one is published and deployed to the gateway.

    apictl import api -f dist/apis/LoansAPI_1.0.0.zip -e dev \
  --params dist/apis/LoansAPI.params.yaml --update --rotate-revision -k
    apictlAPI Manager · Gateway
  14. 37

    Import the API product the same way.

    apictl import api-product -f dist/api-products/JamiiProducts_1.0.0.zip -e dev \
  --update-api-product --rotate-revision -k
    apictlAPI Manager · Gateway
  15. 38

    Run the smoke tests.

    ci/scripts/smoke-test.shci/smoke-tests.txt
    Inside smoke-test.sh
    • Delete and recreate apictl's helper app, then get an OAuth token: apictl get keys -n <API> -v 1.0.0 -e dev
    • For AccountBalanceAPI, which uses API-key security, generate an API key through the Dev Portal REST API: client registration → /oauth2/token → /api/am/devportal/v3/applications/…/api-keys/PRODUCTION/generate
    • For each line in smoke-tests.txt, call the API directly on MI (:8290) and through the gateway (:8243/<context>/1.0.0), then compare the HTTP status. The product is only called through the gateway.
    • Retry gateway calls up to 12 times, 5 seconds apart, while the new revision goes live
    • Fail if any API or product has no line in smoke-tests.txt
    # API | METHOD | path | expected | body
AccountBalanceAPI | GET  | /0022012569822/balance | 200 |
LoansAPI          | POST | /eligibility           | 400 | {}
JamiiProducts     | GET  | /0022012569822/balance | 200 |   # … 9 lines in all
    apictl · curl · jqMI runtimeGatewayDev Portal API
  16. 39

    On success, turn off the safety net and save this CAR as dev's new last-good copy.

    trap - ERR
cp Jamii_WSO2_Project_1.0.0.car $JENKINS_HOME/jamii-state/dev/last-good/

    The log shows “Deployment to dev succeeded: MI CApp + 3 APIs + 1 API product(s)”.

    deploy.sh
  17. 40

    On failure, roll back everything this deploy changed, then fail the stage.

    rollback() in deploy.sh, in this order
    • Delete the smoke-test app, whose subscriptions would otherwise block deleting APIs
    • Delete API products that were new in this run
    • For each imported API, newest first: delete it if it was new, otherwise re-import the backup with --params so it's redeployed to the gateway
    • Re-import the backed-up API products
    • If MI was touched: redeploy the last-good CAR, or remove the new CApp if there was no previous one
    • Print “Rollback complete – dev is back to its previous state”, or “ROLLBACK INCOMPLETE … needs manual attention”

    The rate-limiting tiers from step 32 stay in place.

    deploy.sh · on_error · rollbackapictl · curlAPI ManagerMI

10. Approve and deploy UAT, then prod

stages “Approve: uat” … “Deploy: prod”

These run only if you chose uat or prod in step 2. Otherwise they show as skipped.

  1. 41

    Approve: uat pauses the build and shows “dev is green. Promote to UAT?”. Nothing happens until someone clicks Deploy to UAT or Abort.

    The pause appears in Stage View and in the new graph view, which has buttons for it. The 60-minute timeout keeps counting while it waits.

    youworkflow-aggregator · inputJenkinsfile:58
  2. 42

    Deploy: uat repeats steps 24–40 using ci/environments/uat.properties.

    Today uat.properties has ENABLED=false, so step 25 ends the stage with “placeholder – nothing deployed”. The approval in step 41 is still asked first.

    uat.propertiesdeploy.sh
  3. 43

    Approve: prod (only for DEPLOY_UP_TO=prod) pauses with “UAT is green. Promote to PRODUCTION?”.

    youworkflow-aggregator · input
  4. 44

    Deploy: prod repeats steps 24–40 using ci/environments/prod.properties. That file also has ENABLED=false today.

    prod.propertiesdeploy.sh
